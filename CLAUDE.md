- Consola del cliente, ronda de bugs post-lanzamiento (2026-08-29/30, COMPLETA): Oscar reportó que el login de `/console` "no funciona" (sin ningún error visible). Root-cause real: `src/client/consoleHtml.ts` línea ~485 tenía comillas escapadas UNA vez (`\"Fira Code\"`) dentro del template literal externo de TypeScript que genera `CONSOLE_HTML` — el propio template literal consume ese escape al evaluarse, así que el HTML servido terminaba con comillas SIN escapar dentro de un string de JS, rompiendo la sintaxis de **todo** el `<script>` de la página. Un error de sintaxis en un `<script>` hace que el navegador no ejecute NADA de ese bloque — de ahí que ningún botón respondiera, sin error visible y sin ninguna petición de red (confirmado con `wrangler tail`: la petición de login nunca llegaba al servidor). Corregido doblando el backslash (`\\"..\\"`) para que sobreviva la evaluación del template literal externo y llegue como escape válido al script real del navegador. Verificado renderizando `CONSOLE_HTML` con Node (mismo mecanismo que usa el Worker) y validando la sintaxis del script resultante antes y después del fix — nueva disciplina para este archivo, ya que el bug era invisible a un `grep` superficial. Segundo bug encontrado en la misma ronda, ya en el navegador REAL de Oscar (celular): el menú lateral de `/console` se ocultaba por completo en pantallas ≤800px (`display:none` sin ningún reemplazo), dejando la consola sin forma de cambiar de pestaña en móvil — corregido con el mismo patrón ya usado en el panel admin (`dashboardHtml.ts`): en móvil el menú se vuelve una barra horizontal deslizable en vez de desaparecer. - Backlog de Agencia, "Velocidad de respuesta" — agrupa mensajes seguidos en Telegram (2026-08-30, COMPLETA, criterios definidos con Oscar): tercer ítem del roadmap en el orden confirmado. Alcance acotado con dos decisiones de Oscar: (1) solo Telegram agrupa por ahora — el widget de sitio web se queda con respuesta inmediata en la misma petición, ya que agregarle espera rompería esa promesa sin necesidad real (en un input de texto la gente no manda 3 mensajes seguidos como en una app de mensajería); (2) un solo valor fijo de 12 segundos por ahora, no configurable por tenant todavía. Implementado con **Durable Object Alarms de Cloudflare** (primer uso de esta API en el proyecto) directamente en `ConversationAgent` (`src/agent.ts`): si el llamador manda `bufferSeconds` (>0) en la petición, el mensaje se encola (`state.storage`) junto con los que lleguen en esa ventana en vez de responder ya, y se agenda una alarm; si llega otro mensaje antes de que dispare, se re-agenda (efecto "espera a que termine de escribir"). Al disparar la alarm, todos los mensajes encolados se combinan en un solo texto (unidos por salto de línea) y se procesan como un único turno — una sola llamada al LLM, una sola respuesta, en vez de contestar cada mensaje por separado. La respuesta ya no tiene a quién devolvérsela por HTTP (esa petición terminó hace rato), así que se empuja por el `ChannelProvider` real del canal (Telegram) — best-effort (si el push falla, la respuesta ya quedó guardada en `messages`, solo no le llegó al cliente). Re-chequea `isPaused` justo antes de procesar (por si la conversación se pausó mientras esperaba, ej. un mensaje posterior en el mismo lote pidió un humano). El agente **nunca** decide agrupar mirando el nombre del canal — es el llamador (`index.ts`'s webhook de Telegram, vía nueva constante `TELEGRAM_BUFFER_SECONDS = 12`) quien manda `bufferSeconds` explícitamente; el widget de sitio web (`src/widget.ts`) simplemente nunca lo manda. Lógica del "núcleo" del agente (RAG, calendario, LLM, tools) extraída a un método privado `runAgentTurn` reutilizado tanto por la respuesta inmediata como por la encolada — sin duplicar nada. Verificado en producción con el primer uso real de Alarms en este proyecto: dos mensajes de prueba mandados con 3s de diferencia (endpoint de debug, con un flag temporal agregado solo para esta prueba y revertido después) confirmaron respuesta inmediata `null` en ambos, y 15s después D1 mostró un solo mensaje de usuario combinado ("Hola\n¿Cuál es su horario?") con una sola respuesta coherente del bot — confirmando que no hubo procesamiento duplicado. Datos de prueba limpiados después.

Presentado a Oscar vía pregunta directa: eligió el modelo manual (Partner) para empezar, y el mismo nivel de seguridad ya aceptado para Telegram/Facebook (sin cifrado nuevo, por consistencia y velocidad) sobre el cifrado AES-GCM que pedía el documento. **Implementación**: WhatsApp es un `ChannelProvider` más (`src/channels/whatsapp.ts`) sobre la MISMA infraestructura Meta ya construida (`src/channels/meta.ts` gana `sendWhatsAppMessage`/`sendWhatsAppPhoto`/`subscribeWabaToApp`/`parseWhatsAppWebhookMessages` — mismo Send API/firma HMAC-SHA256/App de Meta, solo cambia la forma del payload y el endpoint). Reto real de diseño: `ChannelProvider.sendMessage(externalId, chatId, text)` solo recibe UN externalId (sin cambiar esa interfaz compartida por Telegram/Facebook/Instagram/Web), pero WhatsApp necesita 2 datos para mandar (de qué número, con qué token) y un tercero (WABA ID) solo para suscribir el webhook una vez al conectar — se resolvió empaquetando los 3 en un externalId compuesto `phoneNumberId|accessToken|wabaId` (documentado, encapsulado: el dashboard pide 3 campos separados como Telegram pide su token, y `POST/PUT /tenants/:id/channels` en `src/admin/routes.ts` los combina server-side — nunca se expone el formato compuesto). El webhook compartido `/webhook/meta` (`src/index.ts`) ahora despacha por `object: "whatsapp_business_account"` además de `"page"`/`"instagram"`, reusando la misma verificación de firma y `platform_settings`. Dashboard: conector "WhatsApp" en `/admin` dejó de estar "Próximamente" — 3 campos (Phone Number ID, WABA ID, tu System User Access Token) + una nota explicando el paso manual irreducible (el cliente agrega a Oscar como Partner en Meta Business Suite — Meta no tiene API para automatizar esto). **Bug real encontrado y corregido durante la verificación** (afecta a TODOS los canales, no solo WhatsApp): ni el webhook de Telegram ni el de Meta envolvían en try/catch el envío final de la respuesta al cliente — un token inválido/revocado o una falla de red al MANDAR (no al recibir) tumbaba con 500 todo el webhook (y, en el caso de Meta, podía cortar el procesamiento de los demás mensajes del mismo lote) pese a que el mensaje del bot ya había quedado guardado en D1 antes de ese punto. Corregido con el mismo criterio "best-effort" ya usado en el resto del proyecto (Vigilante, recupera no-shows). 590 tests (14 nuevos: envío/parseo de WhatsApp en `channels-meta.test.ts`, `channels-whatsapp.test.ts` nuevo, combinación de campos en `admin-routes.test.ts`, canal ya no es "el ejemplo de canal sin adaptador" corregido en 3 archivos de test), typecheck limpio, deploy a producción — **verificado end-to-end en producción de verdad**: creado un tenant desechable (`qa-whatsapp-test`, borrado después), vinculado un canal WhatsApp con credenciales falsas (confirmó que Meta responde con su error real "Invalid OAuth access token" al intentar suscribir el WABA — prueba de que la llamada real está bien formada), y un webhook de WhatsApp simulado con firma HMAC-SHA256 real (usando el App Secret real de `platform_settings`) confirmó el pipeline completo: firma válida → tenant resuelto por `phone_number_id` → agente invocado → LLM real respondió → conversación guardada con `channel: "whatsapp"` → envío de vuelta falló silenciosamente (token falso) sin tumbar la respuesta del webhook (200 "ok"). Lo único que NO se pudo verificar (requiere un número de WhatsApp real, credenciales que no existen todavía) es el envío real exitoso a un destinatario real. Pendiente de Oscar: (1) generar su System User Access Token una sola vez en su propio Business Manager, (2) para el piloto de pádel, conseguir que el cliente lo agregue como Partner de su WABA y darle Phone Number ID/WABA ID, (3) posible blocker igual al de Facebook/Instagram si el mismo App de Meta necesita revisión/verificación adicional para los permisos de WhatsApp — no confirmado todavía, mismo tipo de espera ya documentada para esos conectores.

## Reglas permanentes
- Multi-tenant desde el diseño: todo dato lleva `tenant_id`; nunca 1 deploy = 1 cliente.
- Alta de cliente = configuración (fila en DB), nunca código nuevo por cliente.
- Nuevo giro = nuevo Vertical Template declarativo, cero cambios al core.
- Capa LLM desacoplada vía interfaz `LLMProvider`: OpenAI es el proveedor por default; Anthropic debe poder añadirse sin reescribir el sistema.
- API-first: toda gestión de tenants/verticales existe como endpoint HTTP desde el día 1 — el futuro Skill de Claude solo consumirá esa API, nunca reimplementará lógica.
- No hacer commits/deploys destructivos sin confirmación explícita del dueño (Oscar).
- Al documentar decisiones nuevas, distinguir siempre: CONFIRMADO / INFERIDO / DESCONOCIDO.
- No implementar los superpowers 9-12 (encuestas, no-shows, reseñas, cobros WhatsApp) hasta Etapa 10 — no tienen evidencia de código en Forja, son desarrollo nuevo, no portar nada.
- No usar Basic Auth para admin — JWT/API-key por tenant + Cloudflare Access para super-admin (decisión D10 en el doc de arquitectura).
- No mezclar lógica de vertical/tenant dentro del core.
